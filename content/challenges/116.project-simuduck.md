## Giới thiệu

Bài này refactor đàn vịt từ kế thừa cứng nhắc sang ủy thác. Sau khi làm xong, bạn có thể đổi cánh tên lửa ngay lúc chương trình đang chạy mà không làm vỡ code.

## Kiến thức cần nhớ

### Mùi của code cũ

- Lớp cha ôm hết việc bay, kêu, bơi và hiển thị.
- Vịt cao su kế thừa từ lớp cha nên biết bay một cách sai bét.
- Logic bay bị lặp lại ở nhiều lớp con khác nhau.
- Ví dụ đời thường: như một chiếc remote điều khiển cả nhà, bấm nhầm là cả nhà loạn.
- Muốn thêm một loại vịt mới là phải mở lớp cũ ra vá.

### Strategy tách bay và kêu

- Tách riêng họ hành vi bay: bay bằng cánh, không bay được, bay bằng tên lửa.
- Tách riêng họ hành vi kêu: quạc, chít, im lặng.
- Mỗi con vịt chỉ giữ 2 tham chiếu, rồi ủy thác việc bay và kêu cho các đối tượng đó.
- Ví dụ đời thường: như thay pin hay thay lưỡi dao, các bộ phận đều có thể tháo rời.
- Đổi hành vi lúc chạy mà không ảnh hưởng tới các con vịt khác.

| Việc | Code cũ | Code mới |
|---|---|---|
| Thêm loại vịt | Sửa lớp cha | Thêm lớp mới |
| Đổi cách bay | Ghi đè, vá víu | Gán hành vi mới |
| Đếm tiếng kêu | Đếm thủ công | Observer báo tự động |

### Observer đếm và báo

- Mỗi con vịt là một chủ thể nhỏ, phát đi tin báo mỗi khi nó kêu.
- Bảng đếm và nhà nghiên cứu đăng ký lắng nghe các tin báo này.
- Mỗi tiếng kêu là một tin báo được gửi tự động.
- Ví dụ đời thường: như theo dõi một kênh thì tự nhiên nhận được mỗi lần có tin mới.
- Thêm một bảng mới chỉ cần đăng ký, không phải sửa code của vịt.

## Ví dụ

- Đầu vào: vịt mồi đang chạy xin cánh tên lửa. Kết quả: chỉ riêng nó được đổi cách bay.
- Giải thích: nhờ ủy thác, chỉ cần gán lại một tham chiếu là xong.

```python
# Đổi hành vi lúc chạy không sửa lớp
vit_moi.kieu_bay = TenLua()  # gán hành vi mới
vit_moi.bay()  # bay tên lửa ngay
```

## 💻 Bài tập

Ngôn ngữ: **C++17** (hoặc Java). Đây là một project, dành khoảng 90 phút. Nộp vào thư mục `day-116-simuduck/`.

### Bài 1: Code cũ cần refactor

Viết lại đúng phiên bản "trước refactor" trong thư mục `before/`:

```cpp
class Duck {
 public:
  virtual std::string display() const = 0;
  std::string quack() const { return "Quạc"; }
  std::string fly() const { return "Bay bằng cánh"; }
  std::string swim() const { return "Bơi"; }
};
class RubberDuck : public Duck { /* ghi đè quack bằng "Chít", fly... không ghi đè được vì không virtual */ };
class DecoyDuck : public Duck { ... };
```

Viết test `before_test.cpp` để chỉ ra 3 lỗi: vịt cao su bay được, vịt mồi kêu được, và không thể đổi hành vi lúc chạy.

### Bài 2: Refactor bằng Strategy và Observer

Thư mục `after/`:

| Yêu cầu | Chi tiết |
| --- | --- |
| Strategy | Có 2 họ `FlyBehavior` và `QuackBehavior`. Vịt giữ con trỏ, và các hàm `set...` đổi hành vi lúc chạy |
| Observer | Mỗi vịt là một subject. `QuackCounterBoard` đếm tổng số tiếng kêu. `ResearcherLog` ghi `"<tên>: <tiếng kêu>"` |
| Không phá hành vi | Mọi hành vi đúng ở `before/` vẫn giữ nguyên |
| Mở rộng | Thêm `RobotDuck` (bay bằng tên lửa, kêu "Bíp") chỉ bằng một file mới |

```text
RubberDuck.performFly()                        -> "Không bay được"
DecoyDuck.setFlyBehavior(Rocket); performFly() -> "Bay bằng tên lửa"; các vịt khác không đổi
3 vịt kêu mỗi con 2 lần                         -> board đếm 6, log có 6 dòng
```

### Bài 3: Báo cáo refactor (nâng cao)

Viết `REFACTOR.md`:

1. Sơ đồ lớp trước và sau khi refactor (dùng Mermaid).
2. Bảng liệt kê: yêu cầu thay đổi, số file phải sửa ở `before/`, và số file phải sửa ở `after/`. Có ít nhất 4 yêu cầu (thêm vịt, thêm kiểu bay, đổi bay lúc chạy, thêm người quan sát).
3. Các nguyên lý thiết kế đã áp dụng (đóng gói phần thay đổi, ưu tiên composition, lập trình theo interface), và chỗ áp dụng cụ thể trong code.
