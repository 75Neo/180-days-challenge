## Giới thiệu

Bài này xây bộ chặn các request spam hoặc vượt quá giới hạn. Khi vượt quota, hệ thống trả lỗi 429 và yêu cầu người dùng chờ.

## Kiến thức cần nhớ

### 3 thuật toán giới hạn

- Fixed window: đếm số request trong một cửa sổ cố định, ví dụ mỗi phút.
- Sliding window: lưu timestamp của từng request và tỉa bỏ những cái cũ.
- Token bucket: một thùng nạp token đều đặn, có token thì request mới được qua.
- Ví dụ đời thường: quán chỉ cho 5 khách vào mỗi 10 phút.

### Lưu trạng thái bằng cache

- Mỗi key (user hoặc IP) có một bản ghi đếm riêng.
- Key nào im lặng lâu sẽ tự hết hạn nhờ TTL, nên RAM không bị phình mãi.
- Khóa theo key để đếm đúng khi nhiều luồng cùng gửi request.
- Ví dụ đời thường: mỗi khách có một thẻ đếm riêng, ai lâu không đến thì thẻ bị hủy.

### Chọn thuật toán theo endpoint

- Đăng nhập nên dùng sliding window để chống dò mật khẩu nghiêm ngặt.
- API đọc dữ liệu nên dùng token bucket để thoáng hơn, cho phép burst nhẹ.
- Khi bị chặn, trả về 429 kèm `Retry-After` và các header còn lại.
- Nạp token theo kiểu lười (lazy): chỉ tính số token mới khi có request đến.

| Thuật toán | Điểm mạnh | Điểm yếu |
|---|---|---|
| Fixed window | Rẻ, dễ viết code | Tràn biên cửa sổ, cho phép burst gấp đôi |
| Sliding window | Chính xác | Tốn bộ nhớ để lưu timestamp |
| Token bucket | Cho phép burst mượt | Cần chỉnh tốc độ nạp |

## Ví dụ

- Đầu vào: luật 5 request mỗi phút, gửi dồn 10 request. Kết quả: 5 request được qua, 5 request bị chặn với 429.
- Giải thích: đã hết quota trong cửa sổ nên phải chờ.
- Đầu vào: 50 luồng cùng dùng một key với quota 100. Kết quả: đúng 100 request được qua, không nhiều hơn.
- Giải thích: khóa theo key giúp việc đếm không bị lệch khi các luồng tranh nhau.

## 💻 Bài tập

Ngôn ngữ: **Python 3** (có dùng `asyncio`) hoặc **Go**. Nộp vào thư mục `day-128-ratelimiter/`.

### Bài 1: Ba thuật toán giới hạn

```python
class RateLimiter(Protocol):
    def allow(self, key: str, now: float) -> tuple[bool, float]:
        """Trả (cho phép?, số giây phải chờ nếu bị chặn)."""
```

| Lớp | Tham số | Cách cài đặt |
| --- | --- | --- |
| `FixedWindow` | `limit`, `window` | Đếm theo `floor(now / window)` |
| `SlidingLog` | `limit`, `window` | Deque timestamp cho mỗi key, tỉa bỏ cái cũ |
| `TokenBucket` | `capacity`, `refill_rate` | Nạp lười: tính token mới khi có request |

`now` được truyền vào từ bên ngoài để có thể test bằng đồng hồ giả.

```text
FixedWindow(5, 60): 5 request lúc t=59, 5 request lúc t=60 -> 10 request trong 2 giây đều qua (điểm yếu biên cửa sổ)
SlidingLog(5, 60): cùng kịch bản -> 5 request sau bị chặn
TokenBucket(10, 1/s): 10 request dồn cùng lúc qua hết, request thứ 11 bị chặn, chờ 1 giây
```

### Bài 2: Middleware và dọn dẹp

1. Viết một HTTP server nhỏ (`aiohttp` hoặc `http.server`) với 2 route: `/login` dùng `SlidingLog(5, 60)` theo IP, còn `/api/*` dùng `TokenBucket(20, 5/s)` theo API key.
2. Khi bị chặn, trả về `429` kèm header `Retry-After`, `X-RateLimit-Limit` và `X-RateLimit-Remaining`.
3. Key im lặng quá 10 phút thì bị xóa (TTL). Chạy với 1 triệu key ngẫu nhiên và kiểm tra bộ nhớ không phình mãi.
4. Bảo đảm an toàn khi nhiều request đến đồng thời cùng một key: dùng khóa theo key.

### Bài 3: Đo và giới hạn phân tán (nâng cao)

1. Dùng `wrk`, `hey`, hoặc một script `asyncio` để bắn 5000 request mỗi giây. Đo số request bị chặn có đúng với lý thuyết không, và độ trễ thêm do limiter gây ra.
2. Chạy 2 tiến trình server sau một load balancer giả (round robin). Chỉ ra rằng limiter trong bộ nhớ cho phép lượng request vượt gấp đôi.
3. Chuyển trạng thái sang Redis (`INCR` + `EXPIRE` cho fixed window, hoặc script Lua cho token bucket). Kiểm tra giới hạn đúng trên cả 2 tiến trình.
