# Ngày 128 — App: rate limiter bằng cache và hàng đợi

## 1. Điều kiện tiên quyết

- Ôn lại [Time-Space Complexity](/fundamentals/time-space-complexity): chi phí mỗi request của sliding window O(1)khấu hao với deque, token bucket O(1), bộ nhớ mỗi key O(W) với W là số request trong cửa sổ.
- Ôn lại [Chiều dữ liệu và tính toán](/fundamentals/chieu-du-lieu-va-tinh-toan): mô hình request theo thời gian, burst traffic, ước lượng QPS và RAM cho 100 nghìn keyđồng thời.
- Đã học queue, deque, cache TTL và khóa đồng bộ (tự kiểm: kể được khác biệt fixed window và sliding window, mô tả race condition khi hai request cùng trừ quota).

## 2. Kiến thức trọng tâm

### 2.1. Kiến trúc app

App gồm 4 tầng. Tầng chính sách định nghĩa rule theo key: ví dụ mỗi user 100 request mỗi phút, mỗi IP 1000 request mỗi phút, endpoint đăng nhập 5 request mỗi phút chống brute-force. Tầng engine cài ba thuật toán: fixed window đếm trong cửa sổ cố định, sliding window log lưu timestamp các request trong deque và tỉa cũ, token bucket nạp token đều theo thời gian. Tầng lưu trữ dùng cache có TTL: mỗi key một bản ghi gồm số đếm hoặc deque timestamp hoặc số token và mốc nạp cuối, bọc bằng khóa theo key để serializecập nhậtđồng thời. Tầng middleware đứng trước API mẫu: mỗi request đi qua limiter, cho qua thì gắn header X-RateLimit-Remaining, chặn thì trả 429 kèm Retry-After.

### 2.2. Luồng dữ liệu

Luồng request: trích key từ user-id, IP và endpoint, tra rule tương ứng, lấy khóa theo key, đọc trạng thái từ cache, áp thuật toán quyết định allow hoặc deny, ghi lại trạng thái, thả khóa, trả kết quả kèm header. Luồng nạp token của bucket chạy lazy: không có tiến trình nền, mỗi lần request tới mới tính số token nạp thêm bằng thời gian trôi qua nhân tốc độ, tránh timer toàn cục. Luồng hết hạn chạy bằng TTL của cache: key im lặng quá lâu tự bay, RAM không phình. Luồng giám sát ghi log mỗi quyết định deny để vẽ dashboard tỉ lệ chặn theo thời gian.

### 2.3. Cách kết hợp kiến thức

Hàng đợi deque cho sliding window tỉa đầu cũ O(1)khấu hao; cache có TTL cho lưu trạng thái phân tán với hết hạn tự nhiên; khóa theo key cho correctnessđồng thời mà không khóa toàn cục; token bucket cho phép burst có kiểm soát khác với chặn cứng của fixed window. Ghi chú chuyên sâu: fixed window rẻ nhưng có hiện tượng tràn biên (cuối cửa sổ cũ cộng đầu cửa sổ mới thành burst gấp đôi); sliding window chính xác hơn với chi phí lưu timestamp; token bucket mượt mà cho phép burst tới dung lượng thùng. Chọn thuật toán theo endpoint: đăng nhập dùng sliding window nghiêm, API đọc dùng token bucket thoáng.

### 2.4. Đặc tả module

Module PolicyStore nạp rule từ file cấu hình, hỗ trợ default và override theo endpoint; thay rule không cần restart. Module LimiterEngine cài ba thuật toán với cùng interface allow(key) trả về verdict và retry-after; mỗi allow dưới 1ms ở p99. Module StateCache bọc cache TTL với get, set, compare-and-set hoặc khóa key. Module Middleware tích hợp vào API mẫu, gắn header chuẩn và trang 429. Module LoadTest phát request mô phỏng đều, burst vàđồng thời, đo tỉ lệ chặn và tỉ lệ lọt sai.

## 3. Sau ngày này bạn làm được gì

- Cài đặt ba thuật toán fixed window, sliding window và token bucket với cùng interface verdict.
- Lưu trạng thái limiter bằng cache có TTL và khóa theo key, chịu được requestđồng thời không sai đếm.
- Thiết kế key phân tầng theo user, IP và endpoint với hạn mức riêng và rule override.
- Viết test tải mô phỏng burst, traffic đều vàđồng thời, đo tỉ lệ chặn đúng và tỉ lệ lọt sai.
- Đóng gói middleware limiter chạy được kèm dashboard tỉ lệ chặn theo thời gian thực.

## 4. Bài tập/nhiệm vụ

- Giờ 0.0–0.5: viết PolicyStore và API mẫu 3 endpoint, cài fixed window, test tay 10 request vượt ngưỡng.
- Giờ 0.5–1.0: cài sliding window log bằng deque và token bucket nạp lazy, so sánh hành vi burst bằng kịch bản tay.
- Giờ 1.0–1.5: thêm StateCache TTL và khóa theo key, viết testđồng thời 50 luồng cùng key kiểm tra đếm không lệch.
- Giờ 1.5–2.0: viết LoadTest ba kịch bản, vẽ dashboard tỉ lệ chặn, viết báo cáo chọn thuật toán cho từng endpoint.

## 5. Ví dụ kiểm thử

Deliverable mẫu gồm middleware, rule mẫu và dashboard. Kiểm thử 1: rule 5 request mỗi phút cho endpoint đăng nhập, gửi 10 request dồn dập thì đúng 5 qua 5 bị chặn 429 kèm Retry-After. Kiểm thử 2: hiện tượng tràn biên fixed window được tái hiện bằng kịch bản gửi 5 request cuối cửa sổ và 5 request đầu cửa sổ mới đều qua, còn sliding window chặn bớt; ghi nhận khác biệt. Kiểm thử 3: 50 luồngđồng thời cùng key với quota 100, tổng số request được qua đúng 100 không hơn không kém. Kiểm thử 4: key im lặng quá TTL tự bay khỏi cache, RAM sau test tải quay về mức nền. Kiểm thử 5: token bucket cho burst đúng bằng dung lượng thùng rồi chuyển sang tốc độ đều, đo bằng log timestamp.

## 6. Cạm bẫy

- Quên khóa khi đọc-cập nhật trạng thái: hai requestđồng thời cùng đọc quota 1 rồi cùng cho qua, quota âm; luôn serialize theo key.
- Fixed window tràn biên mà vẫn dùng cho endpoint nhạy cảm: đăng nhập bị brute-force gấp đôi quota ở biên cửa sổ, endpoint này bắt buộc sliding window.
- TTL quá dài giữ key chết: RAM phình theo số user từng ghé, đặt TTL bằng vài lần cửa sổ và đo RAM sau tải.
- Key thiết kế thô (chỉ theo IP): user sau NAT chia nhau quota oan, cần phân tầng user cộng IP cộng endpoint.
- Nạp token bằng timer toàn cục: tốn CPU và phức tạp, dùng nạp lazy theo thời gian trôi khi request tới.

## 7. Tiêu chí chấm

- Mức 1 (chưa đạt): chỉ một thuật toán, chặn sai số lượng, không chịu đượcđồng thời.
- Mức 2 (đạt): đủ ba thuật toán đúng trên test đơn luồng, có middleware trả 429 và header.
- Mức 3 (khá): testđồng thời 50 luồng đếm chuẩn, tái hiện được tràn biên fixed window, dashboard tỉ lệ chặn hoạt động.
- Mức 4 (xuất sắc): báo cáo chọn thuật toán theo endpoint có số liệu, RAM sau tải ổn định nhờ TTL, rule nóng cập nhật không restart, p99 allow dưới 1ms.
