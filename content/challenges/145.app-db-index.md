# Ngày 145 — App: index DB với B-tree, hash và Bloom

## 1. Điều kiện tiên quyết

- Ôn lại [Big-O](/fundamentals/big-o-notation): point lookup hash O(1), B-tree O(log n), range scan O(log n cộng k), ghi có split đắt hơn hash.
- Ôn lại [RAM model và chi phí](/fundamentals/ram-model-va-chi-phi): page đĩa so với RAM, fanout quyết định chiều cao cây, vì sao B-tree sinh ra cho đĩa.
- Đã học hash table nâng cao, Bloom filter và cây BST ở các ngày 4–5, 19, 24 (tự kiểm: giải thích được split nút B-tree và false positive của Bloom).

## 2. Kiến thức trọng tâm

### 2.1. Kiến trúc app

Engine mini gồm 4 tầng. Tầng lưu trữ là file bản ghi append-only: mỗi bản ghi có key số, value chuỗi, offset. Tầng B-tree index key tới offset với nút fanout cấu hình (ví dụ 32), hỗ trợ insert có split lan truyền, point search và range scan bằng duyệt lá liên kết. Tầng hash index ánh xạ key tới offset bằng bảng băm trên RAM cho point lookup cực nhanh. Tầng Bloom chứa toàn bộ key: query key vắng bị chặn trước khi chạm cả hai index. Planner chọn index theo loại query: bằng thì hash (rơi xuống B-tree nếu hash miss để chắc chắn), khoảng thì B-tree, key bị Bloom phủ định thì trả rỗng ngay.

### 2.2. Luồng dữ liệu

Luồng ghi: bản ghi mới append vào file, lấy offset, cập nhật hash index và B-tree (split khi đầy), thêm key vào Bloom. Luồng point query: hỏi Bloom trước, phủ định thì trả rỗng; khẳng định thì tra hash, trúng trả ngay, trượt tra B-tree xác minh (phòng hash trục trặc), cuối cùng đọc bản ghi tại offset. Luồng range query: tra B-tree tìm lá bắt đầu, quét lá liên tiếp tới hết khoảng, đọc loạt bản ghi. Luồng benchmark chạy ba workload (point only, range only, hỗn hợp đọc ghi) đo p50 p95 và thời gian ghi trung bình.

### 2.3. Cách kết hợp kiến thức

B-tree giữ thứ tự cho range query mà hash bó tay; hash cho point lookup O(1) nhanh nhất; Bloom tiết kiệm IO cho key vắng; append-only cộng index tách biệt việc ghi nhanh khỏi tra cứu; fanout lớn giữ cây thấp (3 tầng cho hàng triệu key). Ghi chú chuyên sâu: không có index vạn năng, DB thực tế duy trì nhiều index và planner chọn; Bloom filter là lớp chặn rẻ trước index đắt, đúng vai trò trong LSM-tree và hệ thống lớn; hiệu chỉnh fanout theo kích thước page đĩa chứ không phải số đẹp tùy ý.

### 2.4. Đặc tả module

Module RecordStore append đọc theo offset, checksum cơ bản. Module BTree cài insert split, search, range scan, thống kê chiều cao và số nút. Module HashIndex bảng băm key tới offset, resize khi tải cao. Module BloomGate chặn key vắng, đo false positive thực. Module Planner chọn index theo query và Module Bench đo ba workload.

## 3. Sau ngày này bạn làm được gì

- Cài đặt B-tree insert, split lan truyền và range scan đúng thứ tự.
- Cài đặt hash index point lookup O(1) có resize.
- Tích hợp Bloom filter chặn key vắng, đo false positive thực tế.
- So sánh độ trễ point, range và ghi giữa hai index có số liệu.
- Đóng gói engine index chạy được kèm benchmark ba workload.

## 4. Bài tập/nhiệm vụ

- Giờ 0.0–0.5: viết RecordStore, nạp 50 nghìn bản ghi, kiểm tra đọc offset tay.
- Giờ 0.5–1.0: cài B-tree insert và search, kiểm tra point và range tay.
- Giờ 1.0–1.5: cài hash index và Bloom, kiểm tra chặn key vắng.
- Giờ 1.5–2.0: benchmark ba workload, viết báo cáo chọn index, chốt deliverable.

## 5. Ví dụ kiểm thử

Deliverable mẫu gồm engine, dữ liệu mẫu và báo cáo. Kiểm thử 1: 50 nghìn key point query đúng 100 phần trăm value so với quét file. Kiểm thử 2: range 1000 key trả đúng đủ có thứ tự, không thiếu không thừa. Kiểm thử 3: 10 nghìn key vắng ngẫu nhiên, Bloom chặn trên 90 phần trăm, số còn lại tra index trả rỗng đúng. Kiểm thử 4: point query hash nhanh hơn B-tree ít nhất 2 lần p50; range query B-tree hoàn tất trong khi hash không phục vụ được. Kiểm thử 5: ghi 10 nghìn bản ghi mới không làm hỏng index cũ (point và range sau ghi vẫn đúng).

## 6. Cạm bẫy

- Split B-tree quên lan truyền lên cha: cây mất cân bằng, search lạc; split phải đệ quy tới gốc và tăng chiều cao khi cần.
- Range scan không nối lá: dừng giữa chừng thiếu dữ liệu; lá phải liên kết hoặc duyệt có thứ tự đầy đủ.
- Hash không resize: tải cao, lookup suy biến; ngưỡng tải và resizegấp đôi.
- Tin Bloom khẳng định như chắc chắn: false positive khiến tra index vô ích; Bloom chỉ dùng để chặn phủ định.
- Benchmark range quá nhỏ che giấu chênh lệch: range 10 key thì index nào cũng nhanh; workload phải có range nghìn key.

## 7. Tiêu chí chấm

- Mức 1 (chưa đạt): point hoặc range sai, split hỏng cây, không có Bloom.
- Mức 2 (đạt): point range đúng trên 50 nghìn bản ghi, Bloom chặn được, có benchmark cơ bản.
- Mức 3 (khá): số liệu hash nhanh hơn 2 lần point, range đúng nghìn key, false positive đo được, ghi không hỏng index.
- Mức 4 (xuất sắc): thống kê chiều cao cây và fanout hợp lý, planner chọn index đúng loại query, báo cáo ba workload đầy đủ, tái lập một lệnh.
